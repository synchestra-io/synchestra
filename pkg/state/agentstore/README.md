# pkg/state/agentstore

Backend-neutral implementation of `state.AgentStore` — the `Effort()/Run()/Worktree()/Message()/Activity()/Journal()/Cursor()/Lease()/Health()` sub-store composed on `state.Store` alongside `Task()/Chat()/Project()/State()`.

## Why this package exists

`pkg/state/replication` already abstracts Git/inGitDB and SQLite/DALgo behind one `Journal` interface (`Append`/`After`/`Head`) with role/epoch fencing built in (`RoleFenceError`, `ErrEpochFenced`). Since that abstraction is backend-neutral by design, the effort/run/worktree-claim/message/activity/lease domain logic above it only needs to be written once — here — rather than once per backend (`gitstore`, a future `sqlitestore`, ...). Each backend's `Store.Agent()` method constructs a `replication.Journal` for its own storage and hands it to `agentstore.New`, returning the resulting `*agentstore.Store` directly. See `pkg/state/gitstore/agent.go` for the Git wiring.

## How it works

Every write (`Effort().Create`, `Run().Start`, `Worktree().Claim`, ...) builds a small JSON payload and appends one `replication.Event` through the journal. Every read replays `Journal.After(Cursor{})` and folds the relevant event kinds into an in-memory projection — there is no cached or incrementally-maintained state. This trades read throughput for determinism and simplicity, the same tradeoff `pkg/state/gitstore/board.go` documents for `Task().Board().Rebuild()` scanning every task directory.

Exclusivity (`agent-coordination#ac:one-writer-claim-is-fenced`) and fencing (`state-store/topology#ac:promotion-fences-former-active`) both funnel through `LeaseStore` (`lease.go`): `Acquire` re-derives its "is this resource already held" projection on every retry of a lost sequence race, so two concurrent callers targeting the same resource key can never both succeed — and any Store instance whose configured `AuthorityEpoch` has been fenced out by a promotion recorded through a different Store instance gets `state.ErrLeaseFenced` (wrapping `replication.RoleFenceError`/`ErrEpochFenced`) on its very next write. `WorktreeStore.Claim/Renew/Release/Handoff` (`worktree.go`) delegate directly to `LeaseStore` rather than re-implementing that race handling.

### Lifecycle state machine (task-3)

`Effort`/`Run` each carry a `Status LifecycleStatus` (`planning`/`active`/`handoff_pending`/`awaiting_merge`/`awaiting_push`/`awaiting_cleanup`/`completed`/`aborted`/`failed`/`superseded`/`archived`, per `spec/features/agent-coordination`'s "State machine, merge target, and cleanup") and `EffortStore.Transition`/`RunStore.Transition` append a typed, audited `agent.effort.transitioned`/`agent.run.transitioned` event. `lifecycle.go` owns the one shared `(from -> to)` table both sub-stores validate against; an out-of-table move is refused by wrapping `state.ErrInvalidTransition`, and a move into (or out of) a terminal status (`completed`/`aborted`/`failed`/`superseded`) enforces `CompletionDisposition` is (or is not) set. A new `Effort` starts `planning`; a new `Run` starts `active` (it records an execution attempt already under way). `Transition` re-derives the current status on every retry of a lost sequence race, the same snapshot+`tryAppendAt` shape `Lease().Acquire` and `Cursor().Advance` use.

### Lease TTL/expiry reclaim and voluntary handoff (task-3)

`LeaseStore.Acquire`'s `LeaseAcquireParams.TTL` is now enforced on a wall-clock basis: if the resource's current lease has a non-zero `ExpiresAt` that is not after the caller's observed time, `Acquire` reclaims it in one audited `agent.lease.reclaimed` event instead of returning `ErrConflict` — that single event both marks the abandoned lease released (fencing its old token) and grants the new one, closing the gap a separate "release, then acquire" pair would leave (a crash between the two would strand the resource unreleased). `WorktreeStore.Claim` mirrors this with `agent.worktree.reclaimed`, so the superseded claim is never left dangling as a phantom "active" record. `LeaseStore.Transfer`/`WorktreeStore.Handoff` are the voluntary counterpart: the current holder proves its fence and the SAME lease/claim ID moves to a new holder under a freshly minted fence, in one `agent.lease.transferred`/`agent.worktree.handed_off` event. Expiry is evaluated using each caller's own local clock (normally UTC wall-clock time via `Options.Now`), not a consensus-checked deadline — see `AGENT-coordination`'s `abandoned-run-is-resumable` AC and `lease.go`'s `leaseExpired`.

### Typed negotiation messages (task-3)

`Message`/`MessageSendParams` carry a typed `Kind` (`state.MessageKind`: `coordination.request`/`coordination.proposal`/`coordination.counterexample`/`coordination.decision.accepted`, plus the general-purpose `coordination.note` default) and typed `Evidence []state.EvidenceRef` — no anonymous maps. A `coordination.decision.accepted` message is refused unless it cites at least one `EvidenceRef` (`spec/features/agent-coordination/cross-harness-conformance`: "The accepted decision references the counterexample/test evidence"). The underlying journal/fallback event `Kind` stays exactly `message.sent`/`message.acknowledged` regardless of `Message.Kind` — the typed negotiation vocabulary rides inside that one shared envelope's payload rather than minting new `Kind` strings the Git fallback allowlist (`replication.fallbackKinds`) would also need to grow.

### Close (task-3)

`Store.Close` duck-types the underlying `replication.Journal` for a `Close(context.Context) error` method (mirroring how `replication.GitPushJournal.Close` passes through to its wrapped `Journal`, since `agentstore` depends only on the backend-neutral `Journal` interface, not `replication.BatchedJournal` directly) and delegates to it; a journal without batching (or with it disabled) has nothing pending, so this is a safe no-op. See `pkg/state/gitstore/README.md` and `pkg/state/closeafter.go`'s `CloseAfter` for how a caller uses this to avoid waiting out the group-commit window for a lone `Append`.

## Schema and migration ownership

This package's only persistence surface is the journal, so it has no DALgo table schema to migrate (that belongs to each backend, e.g. `replication.EnsureDALJournalSchema` today, a future `sqlitestore`'s DALgo migrations later). Its schema is the set of event `Kind` strings and JSON payload shapes declared in `schema.go`, each pinned to an explicit version (`.../v1`, `.../v2` for an additive payload change) the same way `replication.EventSchemaV1` and `replication.fallbackKinds` are pinned. A payload change adds a new versioned `Kind` or schema identifier; it never mutates an existing one's meaning in place. `EventKinds()` enumerates the full owned vocabulary. `message.sent`/`message.acknowledged` deliberately reuse the exact strings `replication.fallbackKinds` already allow-lists, so transport-switch reconciliation (task-3's messaging work; the reconciliation import itself remains task-6) has one shared vocabulary rather than two.

## Status

Implements Task 1 (contract surface, Git wiring, claim/lease fencing) and Task 3 (`spec/plans/synchestra-coordination-foundation.md`): the effort/run lifecycle state machine, explicit worktree/lease handoff, lease TTL/expiry reclaim, typed negotiation message kinds/evidence, and `Close`. It deliberately does **not** implement scope-overlap detection (task-7/11), server reconciliation of Git fallback envelopes into the authoritative journal (task-6), the topology `Promote()` administrative workflow (already covered by `pkg/state/replication`), or CLI-level effort/run CRUD verbs (`pkg/cli/agent` only wires the worktree-claim and message verbs task-3's spec explicitly names).

## Open Questions

- `Claim`'s FRESH-acquire path (no existing lease for the resource) still acquires a lease and then appends a `worktree.claimed` follow-up event as two separate journal writes; if the process crashes between them, the lease is held with no matching claim record visible via `Worktree().Get`. `Journal` has no multi-event transaction primitive to close this gap. Task-3 closed the equivalent gap for the RECLAIM and HANDOFF paths specifically (`agent.worktree.reclaimed`/`agent.worktree.handed_off` are each one event covering both the old-claim and new-claim state change) by construction, since those paths already needed a single audited event for fencing correctness; whether the same one-event restructuring is worth applying to the fresh-claim path too (it would need `Lease().Acquire` to expose its about-to-append lease value to the caller before committing, which is a real interface change) is left to a follow-up.
- Message/activity/effort/run writes reuse a fresh event ID as both `EventID` and `IdempotencyKey` on every call, so a client-side retry of the identical logical command is not deduplicated (only the benign "someone else advanced the journal tail" race is retried transparently). Command-level idempotent retry, if needed, is a follow-up.
- `HealthStore.Report` always labels this Store's own perspective `"active"`; it does not yet distinguish a Store wired to a replica-role `Journal`. Task 5/6 (replica workers, promotion) should decide whether that belongs here or in a thin wrapper closer to the topology config.
- **Resolved (task-3).** `LeaseStore.Acquire` now evaluates `LeaseAcquireParams.TTL` against each caller's local clock and reclaims an expired, un-released lease instead of conflicting — see "Lease TTL/expiry reclaim and voluntary handoff" above. Wall-clock expiry is a lower bound only (subject to clock skew across machines, and it is not a consensus-checked deadline); a stricter, skew-tolerant expiry basis is a possible follow-up if this proves insufficient in practice.
- **Resolved (task-3).** `pkg/state/gitstore`'s `Agent()` wiring (`buildAgentCore`) no longer pins its `replication.Journal` to explicit batching-off — it now uses the documented 100-item/1000ms default. This was safe to flip because task-3 also (1) caches the constructed `*agentstore.Store`/journal per `GitStateStore` instance (`gitstore.go`'s `agentOnce`) so concurrent callers on one instance actually share a batch and `Close` reaches the journal that was written to, and (2) wires `Close` through `state.AgentStore`/`state.Store`. A caller that owns a batched journal's lifecycle — a one-shot CLI invocation in particular — MUST call `Close` before process exit for a LONE pending `Append` to return promptly rather than waiting out the window; `state.CloseAfter` (`pkg/state/closeafter.go`) is the safe way to do that, but ONLY around a domain call whose entire execution is exactly one `Head()`-preconditioned `Append` with no other journal read first — see its doc comment for the two distinct failure modes this rules out (a second sequential `Append`, e.g. `state.WorktreeStore.Claim`; or a precondition read via the journal's `After()`, e.g. `Run().Correct`/`Message().Acknowledge`, whose duration is unbounded and grows with journal history unlike `Head()`'s O(1) read — this second failure mode was observed in practice, not just under `-race`, against a real Git-backed journal with a handful of prior events during task-3's own testing, closing what an earlier draft of this bullet under-scoped as only a multi-`Append`/`-race` concern). `pkg/cli/agent` documents exactly which of its verbs use `CloseAfter` (`message send`, `run start`) versus call plainly (`claim`/`renew`/`release`/`handoff`, `message ack`, `run correct`) and why. This residual "no safe grace period for an unbounded pre-read" limitation is not fully closed within the "no `replication` internals beyond its public API" constraint (there is no public "flush but stay open" primitive to build a race-free version on); a future replication API addition exposing an explicit, non-terminal flush trigger would close it properly.
